# Device Management Integration Guide

## Overview

The Device Management system in the HRIS backend is designed to track and manage device bindings for employees. This document explains how the mobile and desktop apps should integrate with this system.

## Database Schema

### DeviceBinding Table

```prisma
model DeviceBinding {
  id            String   @id @default(cuid())
  userId        String
  user          User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  deviceId      String   @unique // Unique device identifier from mobile app
  deviceName    String   // e.g., "Samsung Galaxy S23 (Android)"
  deviceType    String   // "mobile" or "app"
  appVersion    String?  // App version when bound
  bindDate      DateTime @default(now())
  lastUsed      DateTime @updatedAt
  isActive      Boolean  @default(true)

  @@unique([userId, deviceType]) // One mobile device + one app per user
  @@index([userId])
  @@index([deviceId])
  @@map("device_bindings")
}
```

### Key Fields Explained

- **deviceId**: Unique identifier generated by the mobile/desktop app. This is crucial and must be:
  - Unique to the device (cannot be duplicated across devices)
  - Persistent (survives app reinstalls if possible)
  - Not personally identifiable information (PII)

- **deviceName**: Human-readable device name for admin display
  - Mobile example: "Samsung Galaxy S23 (Android)"
  - Desktop example: "MacBook Pro M1 (macOS 14.2)"
  - Web: "Firefox 121 (Windows 10)"

- **deviceType**: Either "mobile" or "app"
  - "mobile": Native mobile apps (iOS, Android)
  - "app": Desktop/web applications

- **appVersion**: Optional version of the app when the device was bound
  - Used to track compatibility issues
  - Format: "1.2.5"

- **bindDate**: Timestamp when device was first bound
  - Used for audit trail and device history

- **lastUsed**: Automatically updated whenever the device:
  - Performs a login
  - Syncs attendance data
  - Fetches any data from the API
  - Used to identify stale/inactive devices

- **isActive**: Boolean flag
  - true = Device can authenticate
  - false = Device is disabled but not deleted (soft delete)

## Device ID Generation Strategy

### Android Apps

Generate a unique device ID using one of these methods (in priority order):

```kotlin
// Option 1: Android ID (recommended - persists across app reinstalls)
val androidId = Settings.Secure.getString(context.contentResolver, Settings.Secure.ANDROID_ID)

// Option 2: IMEI (requires permissions, getting deprecated)
val telephonyManager = context.getSystemService(Context.TELEPHONY_SERVICE) as TelephonyManager
val imei = telephonyManager.deviceId

// Option 3: UUID-based (generated on first run, stored in SharedPreferences)
val uniqueId = UUID.randomUUID().toString()
// Save to SharedPreferences for persistence
```

### iOS Apps

Generate a unique device ID using one of these methods:

```swift
// Option 1: Device Model + UUID (recommended)
let modelName = UIDevice.current.model
let uuid = UIDevice.current.identifierForVendor?.uuidString ?? ""
let deviceId = "\(modelName)-\(uuid)"

// Option 2: UDID (deprecated, avoid)
// let udid = UIDevice.current.identifierForVendor?.uuidString

// Option 3: Generate UUID on first run, store in Keychain
// Keychain ensures persistence across app reinstalls
```

### Desktop/Web Apps

Generate device IDs for desktop and web applications:

```javascript
// Desktop App (Electron/Tauri)
// Generate and persist a machine ID
const machineId = require('machine-uuid').machineId();
// Or use:
const { machineIdSync } = require('node-machine-id');

// Web App (Browser)
// Combination of browser fingerprint + local storage
const deviceId = generateBrowserFingerprint(); // fingerprint2.js
localStorage.setItem('device_id', deviceId);
```

## API Integration Flow

### 1. Device Binding (First Time Setup)

**What the app does:**
```
User Login → Generate Device ID → Send to Backend → Backend creates DeviceBinding record
```

**API Endpoint to call:**
```
POST /api/devices/bind
{
  "deviceId": "unique-device-identifier",
  "deviceName": "Samsung Galaxy S23 (Android)",
  "deviceType": "mobile",
  "appVersion": "1.2.5"
}
```

**Backend response:**
```json
{
  "success": true,
  "message": "Device bound successfully",
  "device": {
    "id": "device_binding_id",
    "userId": "user_id",
    "deviceId": "unique-device-identifier",
    "bindDate": "2024-06-19T10:30:00Z",
    "lastUsed": "2024-06-19T10:30:00Z"
  }
}
```

### 2. Device Authentication Check

**Before allowing login:**
```
User enters credentials → App generates Device ID → Backend verifies:
  - Device is bound to this user
  - Device is active (isActive = true)
  - If new device → Reject or ask for verification
```

**API Endpoint to call:**
```
POST /api/devices/verify
{
  "deviceId": "unique-device-identifier",
  "userId": "user_id"
}
```

### 3. Update Last Used (On Every Sync)

**Every time the app communicates with backend:**
```
App makes any API call → Include device info in headers:
  - X-Device-ID: "unique-device-identifier"
  - X-App-Version: "1.2.5"

Backend automatically updates lastUsed timestamp
```

**Implementation in app:**
```javascript
// Add to all API requests
const headers = {
  'Authorization': `Bearer ${token}`,
  'X-Device-ID': deviceId,
  'X-App-Version': appVersion,
  // other headers...
}
```

### 4. Device Removal (Admin Action)

**Admin removes device binding:**
```
Admin clicks Delete → Backend deletes DeviceBinding record → 
Device can no longer authenticate → User must re-bind device
```

## Backend Server Actions (Already Implemented)

### getDeviceBindings()
Fetches all device bindings for display in admin dashboard.

```typescript
const devices = await getDeviceBindings()
// Returns array of DeviceBinding objects with user details
```

### removeDeviceBinding(deviceId)
Deletes a device binding from the database.

```typescript
await removeDeviceBinding('binding_id')
// Device is now unbound and cannot authenticate
```

### updateDeviceLastUsed(deviceId)
Updates the lastUsed timestamp (called on every API request from the device).

```typescript
await updateDeviceLastUsed('device_id')
// Sets lastUsed to current timestamp
```

### createDeviceBinding(data)
Creates a new device binding. Enforces the "one mobile + one app per user" rule.

```typescript
await createDeviceBinding({
  userId: 'user_id',
  deviceId: 'unique-device-id',
  deviceName: 'Device Display Name',
  deviceType: 'mobile',
  appVersion: '1.2.5'
})
```

## Security Considerations

### Device ID Best Practices

1. **Never use personally identifiable information (PII)**
   - ✅ DO: Use Android ID, IMEI, UDID, UUID
   - ❌ DON'T: Use phone number, email, username

2. **Make Device IDs persistent**
   - Store in secure storage (SharedPreferences, Keychain, LocalStorage)
   - Should survive app uninstall/reinstall if possible

3. **Regenerate on suspicious activity**
   - If app detects jailbreak/root access
   - If device time is significantly off
   - If device location changes dramatically

4. **Include in authentication**
   - Hash device ID with password before sending
   - Verify device ID on every API call
   - Return different session tokens per device

### Rate Limiting

The backend should implement device-based rate limiting:
- Limit login attempts per device ID
- Limit API calls per device per time period
- Alert if suspicious activity detected

## Testing

### Manual Testing Steps

1. **First Device Binding**
   - Install app on device 1
   - Generate device ID and verify it's unique
   - Login and confirm DeviceBinding record is created
   - Check admin dashboard shows the device

2. **Device Authentication**
   - Try login from unregistered device (should fail)
   - Bind device and try again (should succeed)

3. **Last Used Tracking**
   - Check lastUsed timestamp updates on each API call
   - Use timestamp to identify inactive devices

4. **Device Removal**
   - Admin removes device binding
   - Try to login from that device (should fail)
   - User re-binds device (should succeed)

5. **One Device Per Type Restriction**
   - Bind mobile device 1
   - Try to bind mobile device 2 (should fail)
   - Rebind mobile device 1 (should succeed)
